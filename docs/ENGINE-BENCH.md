# 第 3 轮：两个真正的缺陷

## 缺陷 1：代价表**饱和**，三分一的解空间对求解器来说是一样的

`SCALE = 1000`、`BIG = 10**7`，而写入候选表的判断是
`grid = c*SCALE if c < BIG/SCALE else BIG//SCALE` —— 即 **cost >= 10,000 的格全部变成同一个数**。

实测（安柏苑 05 室客厅）：

| 家具 | 可用格 | 被夹顶 | 未夹顶的范围 |
|---|---|---|---|
| 椅子 | 4627 | **622（13.4%）** | 1744..9779 |
| 餐桌 | 1937 | **690（35.6%）** | 2218..5007 |
| 沙发 | 2412 | **759（31.5%）** | 6917..**7124**（只有 3% 落差） |

而 `solve_house` 默认 `exposure=20000` —— 单这一项就能把重家具推到夹顶之上。
**后果**：任何「加强关系权重」之类的改动都会跟着一起撞顶，等于没改。
修法：`BIG = 10**10`。

> ★ 但要诚实记一笔：**把夹顶拆掉之后，成绩一度由 7/10 跌到 4/10。**
> 说明之前那个 7/10 有一部分是夹顶造成的「假性平手」，由 CP-SAT 的任意选择凑巧避开了门口。
> 拆掉夹顶之后求解器开始做**有意识的取舍**，落点就不同了 —— 这不是变差，是**原本就没有稳过**。

## 缺陷 2：门扇区的放宽阶梯可以走到 0.0 —— 门完全开唔到都被接受

`for _frac in (0.6, 0.4, 0.25, 0.0)`：最后一档把门扇扫掠区整个删掉。
实测后果：主人房的床被摆成**床头贴住大门那面墙**，侵占门扇区 0.40 m² ——
因为「挤开门位」可以让其他代价更低。

修法：阶梯收窄到 `(0.6, 0.4, 0.25)`。**「门完全开唔到」永远唔系一个可接受嘅方案。**

# ★ 第 3 轮结论：现在这个「漏放衣柜」是**正确**的

改完之后主人房只剩下床，衣柜被漏放。我原本以为是搜索能力不足 ——
于是写了个暴力枚举去证伪（scripts 里的诊断）：

~~~
睡房可用 2280x2710（6.18 m2），门扇区 0.52 m2
不踩门扇区的候选：床 214 个，衣柜 904 个
>> 两件都放得落、0 硬伤、不踩门扇区的合法排法：0 种
~~~

**一间 6.2 m²（净）的香港睡房，放 1370x1900 的床 + 1900x600 的衣柜 + 一扇 800mm 内开门，
在「床垫贴墙 + 衣柜贴墙 + 不压门扇区」三条规则下，几何上真的无解。**

所以引擎的行为是对的：**当摆不下时，它选择不摆衣柜，而不是去堵门。**
这正好是用户点名要的优先级。

> 这里真正的瓶颈**不在求解器，在家具清单**：
> 1900x600 的衣柜对 6.2 m² 的睡房本来就太大。
> 香港真实做法是 400-450mm 深的推拉门衣柜，或者干脆订造 ——
> 也正好是这个产品存在的理由（跨零售商比价 + 定制家俬）。
> 但这是**顾问层 / LLM 该做的决定**，不是求解器该自己偷偷做掉的。

# 第 4 轮：批量求解器**静静鸡交白卷**（本轮最大发现）

## 现象

用一件固定好的餐桌做障碍，只放 4 张椅子（每张 450x450，4416 个候选格），
_solve_batch 连续 20 秒、60 秒都回 **UNKNOWN**，**返回 0 件**。实测：

    n=1 -> 1 件  OPTIMAL  (4.9s)
    n=2 -> 2 件  OPTIMAL  (7.8s)
    n=3 -> 0 件  UNKNOWN (20.1s)   <-- 交白卷
    n=4 -> 0 件  UNKNOWN (20.1s)   <-- 交白卷

而 _solve_with_order 对批量阶段的返回值没有任何检查 ——
**交白卷 = 那批家具凭空消失**，剩下的布局自然「似随机」。

## 定位

逐项拆解 CP-SAT 模型，找出到底哪一件慢：

| 模型 | 结果 |
|---|---|
| 全部（现状） | UNKNOWN 20.1s |
| **拿掉目标函数** | **OPTIMAL 0.2s** |
| 拿掉 NoOverlap2D | UNKNOWN 20.1s |
| 用乘法代替 AddDivisionEquality | UNKNOWN 20.1s |

→ 慢的是**目标函数**，而且是「用 AddElement(idx, flat, cval) 查表」这种写法。

## 修法（三层，逐层验证）

1. **SCALE 1000 -> 1**：代价值放大一千倍（10^8 量级）喂入 CP-SAT。
   顺带修好一个真 bug —— 旧哨兵值 BIG//SCALE = 10^4 **细过真实代价 10^7**，
   即「不准摆」的格反而比「摆得好」的格便宜。
2. **目标函数改成 table 第 4 栏**：候选 tuple 直接带代价，
   AddAllowedAssignments([x,y,rv,cval], allowed)，目标就是普通线性式，不再用 AddElement。
   → n=3 由「0 件」变「3 件」。
3. **每个朝向只留代价最低的前 150 个候选格**（MAX_CAND_PER_ROT = 150）。
   → n=4 由「0 件 / 20 秒」变「**4 件 / 2.98 秒**」，而且 4 张椅到餐桌
   1082 / 1110 / 1188 / 1207 mm（要求 <= 1155）。

**整个基准的求解耗时由 82 秒降到 20.5 秒。**

> 注：换上 optional fixed-size interval（CP-SAT 标准写法）对这个没有帮助，记录在案以免下次再试。

## 成绩

仍然 7/10，通过的仍然是同一批（床不挡门 / 走得 / 柜门 / 马桶 / 重叠 / 越界 / 沙发朝电视）。
**但底下的可靠性不同了**：求解时间 4 倍改善，而且批量阶段不再静静鸡交白卷。
剩下三条（漏放衣柜与洗衣机、厨房雪柜侵占门扇区 0.19 m2、餐椅 1.4-2.0 米）留待下一轮。

# 第 5 轮：Hub 选错位，卫星就永远塞唔入 —— 餐椅问题解决

## 成续：8/10（首次突破 7）

| 判据 | 之前 | 现在 |
|---|---|---|
| 10 餐椅靠近餐桌 | FAIL，1971 / 1444 / 1082 / 1175 | **PASS，996 / 1033 / 1075 / 1047** |

## 诊断（先证明问题在哪，再改）

对著求解器实际放落的餐桌位置，逐格检查餐椅的候选与代价：

~~~
每张椅 600 个候选格；最近 1075 mm
<=1155 mm（关系要求）的格只有 19 个
<=1155 内最低代价 100 ；全体最低代价 383
~~~

**代价函数是对的**（近桌的格确实更便宜，100 < 383）。
问题系：**近桌只有 19 个可行格，而 4 张 450x450 椅互相重叠，塞唔晒** ——
所以第 4 张只能去 3.3 米外。唔系「摆唔到椅」，系**餐檯一开始就揀咗一个放唔落椅嘅位**。

为什麽会咁：锚定阶段（_place_anchor）系「自己嗰格最靚就揀」，
完全唔知后面仲有嘢要跟住佢。餐桌系 Hub，但佢揀位嗰阵冇人话佢知有 4 张椅。

## 修法（试过两版，第一版更差，记录在案）

- **第一版（失败）**：把「Hub 周围要留位」写成**代价项**加进每格代价。
  结果扰动全屋 —— 餐桌、梳化、电视全部移位，餐椅反而变成 1706-3325 mm（更差）。
  教训：**唔应该用全局代价项去解决「某个锚点自己揀错位」嘅问题。**
- **第二版（成功）**：改成 _place_anchor 里的 **top-40 重排** ——
  先取代价最低的 40 格，再用「周围还剩多少空间放得落卫星家具」(_satellite_room)
  重排。只影响 Hub 自己揀边一格，**唔会污染其他家具嘅代价表**。

配一张主从表 SATELLITES：餐桌->餐椅、书桌->椅、梳化->茶几、床->床头柜、
厨柜台面->灶台/雪柜/洗衣机、电视柜->梳化。

结果：餐桌搬到宽敞处，4 张椅 996-1075 mm，判据 10 变 PASS。

## 还剩两条

1. 漏放 #wardrobe_main（**经暴力枚举证实系几何无解**，正确）同 #washer（重要性最低，正确）
2. 厨房雪柜侵占门扇区 0.19 m2

# 第 6 轮：为什麽「把罚分加高」没有用 —— 没生成过的方案是不会赢的

## 现象

厨房雪柜侵占门扇区 0.19 m2（占 36%）。直觉是「加重罚分逼走它」。

## 先量，再改

对着厨房 4 件家具，穷举 24 种锚定顺序 x 4 种门扇区缩放，
把 key = (硬伤 + 漏放罚分 + 门扇区罚分) 全部列出来：

    缩到 1.00 : 38 (柜台/灶台/洗衣机，门干净)  62 (柜台/雪柜)  73  74  86
    缩到 0.60 : 38 (柜台/灶台/洗衣机，门干净)  62 (柜台/雪柜)  73  74  86
    缩到 0.40 : 38 (柜台/灶台/洗衣机，门干净)  62 (柜台/雪柜)  73  74  86
    缩到 0.25 : 50 (柜台/雪柜/灶台，踩门 36%)  69  70  73  74  82

**38 < 50，也就是「掉雪柜、保持门干净」本来就赢。** 但实际输出是雪柜方案。

## 根因（本轮真正的发现）

查「为什麽 38 没赢」，答案是：**38 那个方案根本没有被生成过。**

- 雪柜在 24 个顺序里面**每一次都「塞得进」** —— 只是塞进了门扇区。
- 求解器不会「主动选择不放一件塞得进的家具」；掉件只在**塞不进**时发生。
- 所以无论把门扇区罚分加到多少（试过 100、300）都没有用：
  **没生成过的候选方案是不会赢的。**

> 教训：**罚分只能在「已经生成的方案之间」排序。**
> 当某个方案从未被生成，加罚分完全无效 —— 要改的是**候选过滤**，不是评分。

## 试过的修法（记录在案，不是所有实验都成功）

把门扇区缩放阶梯的 0.25 档移除（雪柜就进不了门位）：

| | 门扇区 | 漏放 | 柜门打得开 | 总分 |
|---|---|---|---|---|
| 保留 0.25 | FAIL | washer | PASS | **8/10** |
| 移除 0.25 | **PASS** | fridge | **FAIL x2** | 7/10 |

移除之后门干净了，但**洗衣机改为卡死在柜台同灶台的正前方**
（clearance_blocked x2），而雪柜被漏放。所以保留 0.25 档。

## ★ 真正的瓶颈：前方净空被建模成「每件家具私有的整幅矩形」

厨房可用 2120 x 1735。厨柜台面 1700x600，而 FRONT_CLEARANCE["kitchen_counter"] = 900
—— 而且要求**整幅 1700x900 都要空**。

后果：
- 台面自己就吃掉 1700x1500 = 2.55 m2（厨房 69%），剩 235mm 深条带；
- 想「台面 + 灶台 + 雪柜排成一列、共用一条 900mm 通道」？不行 ——
  台面 1700 加灶台 600 = 2300 > 厨房宽 2120，排不进同一面墙；
- 想 L 形转个弯？也不行 —— 台面的 1700 宽前方区会撞到转角那件。

**现实里一条 900mm 通道是服务整排设备的；人是站进去「沿边某一段」用它。**
而引擎要求「每件家具各自独占一整幅 1700x900 领地」。在 3.8 m2 厨房里几何上无解。

## 下一轮（只做一件事）

把前方净空的**硬检查**由「整幅矩形全空」改成
「**沿着前面存在一段 >= 600mm 宽、深 = need 的净空**」（人站得进去的那个宽度）。
预计会同时修好：厨房雪柜踩门、洗衣机卡死柜门 —— 因为排成一列之后
三件共用同一条通道，不再互相排斥。

# 第 7 轮：前方净空改成「沿边一段够阔」+ 门口修复遍

## 改动一：前方净空由「整幅矩形全空」改成「沿边存在一段 >= 600mm 阔」（_front_ok）

上一轮定位的模型缺陷。改完之后：浴室改善（坐厕与洗手盆终于分开摆），
厨房**没有变化** —— 因为厨房的问题不是「净空太严」，是**根本放不下**。

## 改动二：门口修复遍（repair_door_blocks）

收尾时把踩住门扇区的家具移到不踩的位置（其余不动），并加守卫：
**搬位不可以令硬伤数目上升**。

- 不加守卫时：雪柜搬离门扇区，但改为坐正喺柜台前面 -> 多 2 条 clearance_blocked，
  总分 8 -> 7。
- 加守卫后：拒绝这次搬位，维持 8/10。

## ★ 本轮真正的发现：同一组家具，好摆法是存在的，但引擎去不到

厨房 4 件，穷举全部顺序之后出现过嘅方案（用同一个 emap）：

    key  14   counter,fridge,stove      <-- 不踩门扇区
    key  38   counter,stove,washer
    key  51   counter,fridge,washer
    key  62   counter,fridge
    key  73   fridge,stove,washer
    key  86   counter,washer
    key  87   counter,stove

但 solve_cpsat 实际交返嚟嘅系：

    counter,fridge,stove  ->  key = 0 硬伤 + 12 漏放 + 107 门扇区 = 119

**同一组三件（柜台/雪柜/灶台），明明有一个 key 14（唔踩门）嘅排法，
引擎交返 key 119 嘅版本。**

原因：
1. 锚定係**逐件贪心** —— 24 个顺序只係换次序，**没有一步会「同一批件、唔同位置」再试**。
2. 门口修复遍（今轮新增）本来想补呢个洞，但喺呢个厨房里，
   佢搵到嘅所有「唔踩门」嘅位都会挡住柜台 -> 被守卫拒绝。
   （即係修复遍嘅候选搜索太粗：200mm 网格 + 只搬一件 + 其余冻结。）

**瓶颈已经收窄到：位置搜索只有「贪心 + 局部修复」，缺少「同一批件、全局重排」嘅一步。**

## ⚠️ 同时必须讲清楚：呢个厨房本身就系超编

3.8 m2 厨房 + 一扇 800mm 内开门，放 1700 柜台 + 灶台 + 雪柜 + 洗衣机：
无论点排，都係「踩门 / 挡柜台 / 漏放一件」三选一。
**呢个唔係求解器问题，系家具清单问题** ——
真实做法係换 1200 柜台、或者把厨房门改推拉门。
呢个决定应该由顾问层（LLM）做，唔应该由求解器静静鸡帮客户做掉。
