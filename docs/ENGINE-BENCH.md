# 第 3 轮：两个真正的缺陷

## 缺陷 1：代价表**饱和**，三分一的解空间对求解器来说是一样的

`SCALE = 1000`、`BIG = 10**7`，而写入候选表的判断是
`grid = c*SCALE if c < BIG/SCALE else BIG//SCALE` —— 即 **cost >= 10,000 的格全部变成同一个数**。

实测（安柏苑 05 室客厅）：

| 家具 | 可用格 | 被夹顶 | 未夹顶的范围 |
|---|---|---|---|
| 椅子 | 4627 | **622（13.4%）** | 1744..9779 |
| 餐桌 | 1937 | **690（35.6%）** | 2218..5007 |
| 沙发 | 2412 | **759（31.5%）** | 6917..**7124**（只有 3% 落差） |

而 `solve_house` 默认 `exposure=20000` —— 单这一项就能把重家具推到夹顶之上。
**后果**：任何「加强关系权重」之类的改动都会跟着一起撞顶，等于没改。
修法：`BIG = 10**10`。

> ★ 但要诚实记一笔：**把夹顶拆掉之后，成绩一度由 7/10 跌到 4/10。**
> 说明之前那个 7/10 有一部分是夹顶造成的「假性平手」，由 CP-SAT 的任意选择凑巧避开了门口。
> 拆掉夹顶之后求解器开始做**有意识的取舍**，落点就不同了 —— 这不是变差，是**原本就没有稳过**。

## 缺陷 2：门扇区的放宽阶梯可以走到 0.0 —— 门完全开唔到都被接受

`for _frac in (0.6, 0.4, 0.25, 0.0)`：最后一档把门扇扫掠区整个删掉。
实测后果：主人房的床被摆成**床头贴住大门那面墙**，侵占门扇区 0.40 m² ——
因为「挤开门位」可以让其他代价更低。

修法：阶梯收窄到 `(0.6, 0.4, 0.25)`。**「门完全开唔到」永远唔系一个可接受嘅方案。**

# ★ 第 3 轮结论：现在这个「漏放衣柜」是**正确**的

改完之后主人房只剩下床，衣柜被漏放。我原本以为是搜索能力不足 ——
于是写了个暴力枚举去证伪（scripts 里的诊断）：

~~~
睡房可用 2280x2710（6.18 m2），门扇区 0.52 m2
不踩门扇区的候选：床 214 个，衣柜 904 个
>> 两件都放得落、0 硬伤、不踩门扇区的合法排法：0 种
~~~

**一间 6.2 m²（净）的香港睡房，放 1370x1900 的床 + 1900x600 的衣柜 + 一扇 800mm 内开门，
在「床垫贴墙 + 衣柜贴墙 + 不压门扇区」三条规则下，几何上真的无解。**

所以引擎的行为是对的：**当摆不下时，它选择不摆衣柜，而不是去堵门。**
这正好是用户点名要的优先级。

> 这里真正的瓶颈**不在求解器，在家具清单**：
> 1900x600 的衣柜对 6.2 m² 的睡房本来就太大。
> 香港真实做法是 400-450mm 深的推拉门衣柜，或者干脆订造 ——
> 也正好是这个产品存在的理由（跨零售商比价 + 定制家俬）。
> 但这是**顾问层 / LLM 该做的决定**，不是求解器该自己偷偷做掉的。
