# 实验：不给求解器，让 LLM 直接输出坐标

问题（用户 2026-10）：**「假设没有中间引擎，只有 LLM、客户需求、家具 list，
能不能让 LLM 直接操作生成准确的 floor plan？」**

脚本：scripts/llm_direct_layout_test.py　原始输出：out/llm_direct_layout.json
测试空间：Farnsworth House，16840 x 8656mm 的开放空间 + 中央 7506 x 3816mm 实心服务核心。
给 LLM 的信息与给引擎的**完全一样**：房间尺寸、核心矩形坐标、门洞位置、22 件家具的精确尺寸、坐标约定。

---

## 结果

### 第一次（max_tokens = 8000）：0 / 3 次产出有效答案

3 次全部 finish_reason=length，8000 个输出 token 全部用在**用散文推演布局**上，
一个字都还没写进 JSON。摘一段它当时在想什么：

> 所以调整床 y 从 800 开始：床 y 800..2800。衣柜 y 0..650 不重叠。
> 但床头柜要放床头旁边：床头是北端 y=800。床头柜放床两侧？床宽 1800（x 1100..2900）。
> 床头柜 450x450 放在床头一侧，比如 x 2900..3350, y 800..1250。可以。
> 但衣柜在 y 0..650 上方，中间留 150 空隙，有点小

推理本身是**合理**的 —— 它在做分组、在查重叠、在退让。它只是**想不完**。

### 第二次（max_tokens = 32000 + 强制「以 [ 开头」）：2 / 2 次产出 22 件完整坐标

| 指标 | LLM run 1 | LLM run 2 | 本引擎 | 真人原设计 |
|---|---|---|---|---|
| 完整落在房间内 | 13 / 22 | 15 / 22 | **22 / 22** | 22 / 22 |
| **压在实心服务核心里面** | **9 件** | **7 件** | 0 | 0 |
| 互相重叠 | 1 对 | 2 对 | 0 | 0 |
| 硬伤 | 5 条 | 6 条 | 0 条 | 4 条 |
| 从大门走不到 | 1 件 | 2 件 | 0 | 0 |

压进核心的 9 件是：chaise1、chaise2、daybed、risom1、risom2、cocktail、slipper1、slipper2、bed。

**整个起居组 + 床，全部摆在房间正中央 —— 那里正好是一整块实心核心
（厨房台面 + 两个卫生间 + 机电 + 壁炉）。**

这不是随手乱放。语义上「起居区应该在房子中间」完全正确 ——
它只是不知道那个中间是**实心的**。这就是「LLM 懂意思、不懂空间」最干净的一个例子。

## 但同一个实验也给出了反过来的结论

看功能关系距离（mm）：

| 功能关系 | LLM run 1 | LLM run 2 | 真人原设计 | 本引擎 |
|---|---|---|---|---|
| 餐椅 1 - 餐桌 | 1047 | 1024 | 847 | **15297** |
| 餐椅 2 - 餐桌 | **730** | 830 | 822 | **10209** |
| 餐椅 3 - 餐桌 | 1047 | 1086 | 1276 | 1458 |
| 餐椅 4 - 餐桌 | 1047 | 1024 | 1265 | 1774 |
| 餐椅 5 - 餐桌 | **730** | 830 | 835 | 1269 |
| 餐椅 6 - 餐桌 | 1047 | 1086 | 808 | **15285** |
| 床 - 床头柜 | 1505 | 1604 | 1864 | **14674** |
| 书桌 - 书桌椅 | 810 | 700 | 800 | **5296** |
| 茶几 - 沙发 | 1000 | 1500 | 2202 | 1189 |

**LLM 的功能关系比本引擎好一个数量级，而且几乎和真人方案一样准。**
6 张餐椅全部落在餐桌 730-1086mm 以内 —— 引擎有 2 张在 15 米外。

代价是 token：run 1 用了 **21122 个输出 token 的思考**，只换来 1196 字符的坐标。

## 结论：不是「要不要引擎」，是**分工画错了位置**

| | 语义 / 关系 | 毫米 / 几何 |
|---|---|---|
| LLM | **强**：分组、谁挨着谁、成对、区域该放哪 | **弱**：41% 的家具摆进实心块里 |
| 本引擎 | **弱**：只有 5 条关系规则，餐椅不认识餐桌 | **强**：不重叠、不出界、不压核心、走得到 |

两者**恰好互补**，而且互补的方向正好说明现在的分界线错了：

- 现在引擎被要求**猜语义**（用 5 条硬编码关系 + 一个「贴墙 + 低曝光」的目标函数），猜得很差；
- 现在 LLM 被要求**闭嘴**（prompt 第一条硬规则就是「绝对不要输出坐标」），
  于是它唯一能做的就是在可行性问题上打转。

正确的分界线是：

~~~
LLM  ->  区（zone）+ 组（group）+ 组内关系（谁挨着谁 / 谁面对谁 / 谁成对）
引擎 ->  在给定的 zone 和关系下，解出毫米级坐标，并保证不重叠 / 不越界 / 不压核心
~~~

这样 LLM 一个毫米都不用数，引擎一句人话都不用猜。

### 附带发现：视觉负荷这个指标可以被「非法方案」骗到

LLM 那两份**把 9 件家具塞进实心核心**的方案，视觉负荷是 0.0137 / 0.0177，
**比本引擎的合法方案（0.01733）还低**。
因为重叠和压在核心里的家具位置恰好是「低曝光」的。

所以视觉负荷分**必须**和合法性检查一起看，单独拿出来排名会奖励垃圾方案。
这条对 Demo 里的「显大分」展示同样成立。

## 外部佐证

FloorplanQA（ICML 2026，arXiv 2507.07644）：15 个 LLM x 2000 份 JSON 户型 x 16000 道几何题。

- Placement（判断一个摆法是否满足约束）：合成矩形 60-85%，真实多边形户型 64.5%
- Repositioning（给一件家具找一个满足约束的新位置）：真实户型 **47.0%**
- Free Space / Max Box / Shortest Path（自由空间 / 最大可放矩形 / 最短路径）：**5-45%**，真实户型 < 30%
- 给它 Python 解释器：算术题 +30~43pp，但 Max Box **-4.5**、Shortest Path **-12.5**
  —— 「瓶颈在算法层，不是在算术精度」
- 把标签 sofa / chair 互换、几何完全不动：Repositioning 从 60.5% 掉到 **40.0%**
  —— 证明模型在靠「沙发 = 大家具」这种语言先验，**不是在读坐标**

把单件成功率乘起来：22 件都要成立，单件 95% -> 0.95^22 = 32%；
单件 80% -> 0.7%。而且还要 231 对互不重叠。
**这就是为什么「直接让 LLM 出坐标」在生产上不成立** —— 不是模型笨，是任务形态不匹配：
自回归逐件生成 vs 全局耦合约束。
