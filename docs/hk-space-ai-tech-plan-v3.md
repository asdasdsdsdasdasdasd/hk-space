## 0. 一句话定义

> 用户给出**整间屋的户型 + 需求**（或直接给一份家具清单），系统在**墙体不可动、家具买成品**的约束下，算出**视觉上最显大、同时所有家具都放得下、动线走得通**的整屋 3D 布置方案。

## 1. 三个必须先想清楚的事

### 1.1 竖向是香港真正的主战场

一个 28m²（约 300 尺）的单位，层高 2.5m：

| | 面积 |
|---|---|
| 地板可用面积 | **28 m²** |
| 墙面可用面积（周长 22m × 2.5m） | **55 m²** |

**墙面可用面积是地板的两倍**，而地板还要被走道吃掉一大半。香港人挤，本质上是**只用了三分之一的可利用表面**。

所以「把柜子放高处」「床架高、床下放桌」不是锦上添花，是这个产品的核心逻辑。任何 2D 平面的方案都注定失败。

### 1.2 显大 ≠ 少放东西，而是三件事

这是整个产品最核心的认知：

> **「视觉显大」不是「减少家具体量」，而是「把体量集中到看不见的地方」。**

香港的单位不可能真的少放东西——收纳是刚需。所以正确的解法是三条可计算的子目标：

| # | 子目标 | 直觉 | 可计算吗 |
|---|---|---|---|
| ① | **主视线通畅** | 进门一眼能看到窗，房间就"深" | 几何精确可算 |
| ② | **体量集中** | 到顶柜全挤在一面不显眼的墙上，比分散在三面墙好得多 | 可计算（可见性加权） |
| ③ | **视觉重量轻** | 浅色、通透、玻璃、镜面比深色实木"轻" | 可计算（来自选品属性） |

**一个真正的优化器在这三件事上有巨大发挥空间。** 同样一套家具，摆得好的和摆得差的，主观感受能差一倍——而家具一件都没少。

### 1.3 显大 vs 收纳的根本张力，以及解法

这是香港室内设计的核心矛盾：**到顶柜是收纳之王，但视觉上杀房间。**

解法不是二选一，而是**分工**：

- **家具清单是硬约束**：清单上的东西必须全部放得下（用户要收纳）
- **摆放是优化目标**：在放得下的所有方案里，选最显大的那个

但如果清单本身就是「5 个 2.4m 高柜」——那任何摆法都救不了。所以系统必须能**反过来对清单提意见**：

> 「这一面墙如果放 2.4m 到顶柜，会把客厅视觉上切成两半。换成 1.8m 柜 + 上方开放式层架，收纳只少 12%，但显大很多。要试试吗？」

**这是 LLM 的活，而且是这个产品最值钱的功能之一。** 用户自己想不到，设计师会想但收费贵。

## 2. 「视觉显大」怎么变成可计算的目标函数

这是 v3 最核心的技术贡献。文献支撑：isovist 分析（Benedikt, 1979）、visibility graph analysis（空间句法）、Stamps (2011) 关于面积/高度/长宽比/颜色对 spaciousness 影响的实验研究。

### 2.1 三层指标体系

| 层 | 指标 | 怎么算 | 用在哪 |
|---|---|---|---|
| **L1 几何可见性** | isovist 面积、可见地板占比、遮挡角、天际可见度 | 射线投射 + Shapely，毫秒级精确 | **进求解器目标函数** |
| **L2 感知属性** | 明度、通透度、视觉体量、反光率、杂乱度 | 从 SKU 属性 + 布局算 | **进排序与选品** |
| **L3 学习评分** | "哪个更显大"的偏好分 | VLM 成对比较 → 偏好模型 | **Top-K 最终重排** |

**关键分界**：L1 可以进 CP-SAT（线性化后），L2 影响选品，L3 只做最后从 5 个方案里挑 1 个。

### 2.2 Isovist（等视域）

**定义**：从某个视点出发，360° 射线投射不被遮挡的可见区域多边形。

```python
import numpy as np
from shapely.geometry import Polygon, LineString, Point

def isovist(room_poly, obstacle_polys, viewpoint, n_rays=180):
    """从 viewpoint 计算等视域多边形"""
    angles = np.linspace(0, 2*np.pi, n_rays, endpoint=False)
    hits = []
    for a in angles:
        ray = LineString([viewpoint,
                          viewpoint + 20000*np.array([np.cos(a), np.sin(a)])])
        d_wall = ray.intersection(room_poly.boundary).distance(viewpoint)
        d_obs = min([ray.intersection(o).distance(viewpoint)
                     for o in obstacle_polys if ray.intersects(o)], default=1e9)
        hits.append(viewpoint + min(d_wall, d_obs) * np.array([np.cos(a), np.sin(a)]))
    return Polygon(hits)

def isovist_metrics(iso, room_poly):
    A, P = iso.area, iso.length
    return {
        "area": A,
        "compactness": 4*np.pi*A / (P**2),          # 越接近 1 越开阔，越小越"堵"
        "visible_floor_ratio": A / room_poly.area,  # 文献中最强的单项预测因子
    }
```

**关键视点**（每个都要算）：
- **入口**（进门第一眼最重要）
- **房间几何中心**
- **主要停留点**（沙发座面、床沿、餐椅）
- **走道中点**

### 2.3 遮挡立体角

从 1.5m 眼高看出去，高家具挡住了多少视野。

```python
def occlusion_angle(obstacles, viewpoint, tall_threshold=1200):
    """返回被高家具遮挡的水平角度占比 (0-1)"""
    intervals = []
    for o in obstacles:
        if o.height_mm < tall_threshold:
            continue
        a1, a2 = azimuth(o.p1, viewpoint), azimuth(o.p2, viewpoint)
        intervals.append(sorted_angle_interval(a1, a2))
    return merge_and_measure(intervals) / (2*np.pi)
```

### 2.4 可见性频次图 —— 让「体量集中」变成可优化的东西

这是把 1.2 的洞察②变成数学的关键技巧：

```python
# 离线预计算一次：房间栅格化 (50mm)，对每个关键视点算可见性
vis_count = np.zeros_like(grid)                   # 每格被几个视点看得见
for vp in key_viewpoints:
    vis_count += rasterize(isovist(room_poly, [], vp), cell=50)

exposure = vis_count / len(key_viewpoints)        # 归一化 0-1 的"曝光度"
```

**然后目标函数就变成一句话：**

> **把视觉体量大的家具，放到曝光度最低的格子上。**

```python
visual_mass(item) = footprint_area * height * opacity * (1 - lightness/100)

objective += W_mass * sum(-visual_mass(item) * exposure(position(item)))
```

预计算的 `exposure` 是**静态的**（不含家具），这让目标函数保持线性，可以直接进 CP-SAT。家具之间的相互遮挡用迭代精修处理。

#### ⚠️ 实现阶段的三个重要发现（`packages/geometry` 实测）

**① 公式必须乘上「显著性」，不能只数可见性。**

只算「被几个视点看得见」不够 —— **看得见和碍眼是两回事**。一个 2.2m 高的柜子站在门口 1 米处占据大半个视野；同样的柜子放在 4 米外的角落，视觉压迫小得多。所以要加距离衰减：

```
exposure(cell) = normalize( Σ_v  w_v · visible_v(cell) / (1 + d(v, cell)/D0) )
```

校准值：`w_entrance = 6.0`（进门第一眼最重要）、`D0 = 800mm`。

**② ★ 曝光度在「凸的矩形空房间」里会退化成纯距离。**

矩形空房间里任何一点都看得见任何一点，`visible` 恒等于 1，曝光度就只剩距离项。**它真正发挥作用需要两个条件：**

| 条件 | 说明 |
|---|---|
| **非凸户型** | L 形 / 凹位 / 入門玄關 —— 香港极常见，能在房间里造出真正的「遮挡阴影」 |
| **家具互相遮挡** | 常态 |

**这是对输入层的一个隐含要求**：如果用户给的是规规矩矩的矩形房间，这个指标会失效，必须靠视觉走廊 + 遮挡角补上。演示户型因此改用 L 形。

**③ 所有阈值都是校准出来的，不是拍脑袋定的。**

`packages/geometry/hkgeometry/_calibrate.py` 是参数扫描脚本。校准依据：让「衣柜放门口 vs 放低曝光区」在 `visual_mass_exposure` 上产生最大分离（实测 **0.63 → 0.41**）。

> ⚠️ 这些值**几何上自洽，但尚未经过人类感知验证**。它们对不对得上人的感觉，要靠 §2.7 的 VLM 成对比较来校准 —— **这正是 M1 排在 M3（训 Transformer）之前的原因：先校准靶子，再造子弹。**

**这个技巧的威力**：它让「到顶柜集中在一面不显眼的墙上」从一个美学直觉，变成一个可以被求解器优化的数值目标。

### 2.5 视觉走廊（sightline corridor）

比完整 isovist 更简单、更鲁棒的近似，也更容易进求解器：

```python
# 定义 K 条关键视廊
corridors = [
  (entrance, window_main),      # 进门 → 主窗
  (sofa_center, window_main),   # 沙发 → 主窗
  (entrance, room_deepest_pt),  # 进门 → 房间最深处
]

def corridor_penalty(corridor, items):
    pen = 0
    for it in items:
        seg = corridor.intersection(it.footprint)
        if seg.length > 0:
            # 超过 1100mm（眼高以下不算挡）才罚，越高罚越多
            pen += max(0, it.height - 1100) * seg.length
    return pen
```

**目标：让所有关键视廊上的家具高度都 < 1100mm。** 这条规则简单、可验证、效果极好，而且用户可以理解（"进门要能看到窗"）。

### 2.6 感知属性来自选品，不在几何里

**这是「买成品」这个前提带来的一个关键推论：**

> 因为买成品、尺寸不可调，**「选品」对显大的影响甚至大于「摆放」**。

同样一个 800×400 的位置，放**深色实木封闭柜**和放**浅色开放格柜**，视觉体量差 3 倍。摆法完全相同。

所以 **SKU schema 必须新增感知属性字段**（见 4.2），而且**目录检索必须目标感知**：

```python
# 旧的检索：能放下就行
query_catalog(category="wardrobe", max_w=800, max_d=400)

# 新的检索：能放下 + 视觉体量低
query_catalog(category="wardrobe", max_w=800, max_d=400,
              minimize="visual_mass", prefer={"reflectivity": (">", 0.5)})
```

**镜面和玻璃是香港最便宜的「显大」手段**，目录里必须能筛出来。

### 2.7 VLM 成对比较 → 偏好模型（L3）

几何算得出「可见地板占比」，但算不出「这个米色木纹看起来比那个深胡桃木轻多少」。这部分交给 VLM：

```
对 Top-K 方案两两配对：
    渲染两张等轴测图 + 两张第一人称视角图
    -> 问 VLM：「哪个空间感觉更大？为什么？」
    -> 收集 1000 组偏好对
    -> 训一个小的偏好模型（Bradley-Terry / 用 CLIP embedding 回归）
    -> 之后可以秒级给任意布局打"显大分"
```

**注意**：VLM 只用在**最终从 5 个方案里挑 1 个**，以及**生成偏好训练数据**。不要让它进优化循环（太慢、不稳定）。

### 2.8 视觉诊断与解释（产品功能）

既然目标是感知的，系统就不该默默优化，而应该**说出问题在哪**：

> **现在让它显小的 3 个原因：**
> ① 沙发背对入口，进门形成视觉屏障（遮挡进门视线 42%）
> ② 电视柜高 1.2m，正好在眼高附近，挡掉一半横向视野
> ③ 深色实木衣柜在进门最显眼的位置，视觉体量占全屋 38%
>
> **可以这样改：**
> • 电视柜换 1.2m→0.45m 的矮款（搜索结果：¥680 起）
> • 衣柜挪到左侧凹位，进门看不见
> • 沙发换通透款（有腿、能看到底下地板）

**这是用户能立刻感知价值的地方，也是最容易被分享传播的地方。**

## 3. 问题建模：整屋 3D

### 3.1 三层分解（不要把整屋塞进一个求解器）

```
┌─ Level 1 ─ 房间功能分配 ─────────────────────────┐
│  输入：户型 + 來去水位/煤氣喉 + 家庭构成 + 家具清单│
│  输出：每件家具归到哪个房间                        │
│  规模：20 件 × 5 房 = 小规模 CP-SAT，秒级          │
│  管线是锚：厨房厕所被來去水位钉死                  │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ Level 2 ─ 房间内 3D 布局（并行，32 核）─────────┐
│  每间房独立：[Transformer 提议 → CP-SAT 精修]      │
│  变量：(x, y, z, rot) + 支撑关系                   │
│  每房 2-4s，5 房并行 → 墙钟仍是 2-4s               │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ Level 3 ─ 跨房间全局校验 ──────────────────────┐
│  动线连通（图论）· 门轴被挡 · 隐私梯度 · 视线贯通  │
│  毫秒级                                            │
└──────────────────┬───────────────────────────────┘
                   │ 有违规
                   ▼
        只重解出问题的那几间房 ──┐
                   ▲            │
                   └────────────┘
```

**这就是把「整屋联合最优」变成可解的办法**：不联合求解，分层求解 + 定向重解。学术上叫 Benders 分解 / 坐标下降。

**而且这个结构天然并行**，正好用上 32 核。整屋出方案目标延迟 **5–15 秒**。

### 3.2 竖向：分层 2.5D + 支撑关系

**不能做**：把整屋离散成三维体素跑一个 CP-SAT。8m×8m×2.5m，100mm 分辨率 = **16 万格**，直接超时。

**正确做法**：香港的成品家具 95% 是轴对齐的盒子，竖向放置。把每间房切成可用层：

```
层 3  顶部     2000 – 层高     ← 到顶柜上层、换季储物（需梯子，可及性差）
层 2  上层     1400 – 2000mm   ← 高架床、吊柜、到顶柜中段
层 1  使用层    400 – 1400mm   ← 桌面、沙发、床垫、矮柜
层 0  地面层      0 –  400mm   ← 床底抽屉、鞋柜下层、地台收纳
```

**每一层退化成一个 2D 问题**（就是 v2 里那套方法），层间用**支撑约束**连接：

```
support(吊柜, 墙)                 吊柜挂墙，需要墙体类型允许
headroom(高架床, 下方, 750mm)     床下要塞得下坐着的人
reach_max(到顶柜, 1800mm)         超过 1800mm 只能放换季
clear(家具顶面, 该处梁底)          顶不撞梁
```

### 3.3 成品家具下，3D 有哪三种手段

因为买成品、尺寸不可调，**竖向空间的利用方式被限制为三种**（这既是约束也是机会）：

| 手段 | 说明 | 例子 | 需要的数据字段 |
|---|---|---|---|
| **① 本身就多层的成品** | 买来就是立体的，最省事 | 高架床（床+书桌一体）、油壓收納床、上下鋪、儲物地台床 | 无（就是普通 SKU） |
| **② 壁挂 / 吊柜** | 高度自由，不占地板 | 吊柜、壁掛書桌、壁掛層架 | `mount: wall`、`wall_type_required` |
| **③ 承托堆叠** | 在矮柜上放小柜、桌面放架子 | 有限制 | `can_support: {max_load_kg, top_polygon}` |

**重要的安全约束：不要允许任意堆叠。**

成品家具的承重和稳定性没有保证，把一个大柜子摆在另一个柜子上，视频里看着行，现实中会倒。所以：

> **只有当 SKU 显式标注了 `can_support`（最大承重 + 顶面可用多边形）时，才允许在上面放东西。**

这条规则同时也让求解空间大幅缩小。

### 3.4 高度场：层高不是常数

```python
# 每间房有一张高度场，家具顶部不能超过它
z_max(x, y) = 层高
            - 该处梁下压量（横梁 200-350mm）
            - 局部假天花
            - 冷气机 / 热水炉占用

# 窗台是特殊区域：窗台高 450-600mm，窗台面上是可用的
z_sill(x, y) = 窗台高
```

**这件事必须在建模时处理，不能事后检查**——不然求解器会兴高采烈地把到顶柜怼进横梁里。

## 5. 输入层：房间与需求怎么进系统

> **已确定策略：以「上传户型图」为主入口。**

### 5.1 用户手上有什么

| 来源 | 是否带尺寸标注 | 占比 | 处理难度 |
|---|---|---|---|
| 楼盘平面图（中介 / 發展商售樓書） | 多数有 | 高 | 低 |
| 差餉物業估價署 / 屋宇署图则 | 有 | 低 | 低 |
| 裝修公司草图 / 手绘 | 部分有 | 中 | 中 |
| 手机拍的平面图照片（有遮挡、透视变形） | 多数有 | **高** | **高** |
| 只有现场照片，没有图 | 无 | 中 | 高 |

**关键事实：香港的户型图绝大多数带尺寸标注**（mm 或 呎）。这是巨大优势——**能读到标注数字，就不必靠视觉猜比例尺**，精度直接上一个数量级。

### 5.2 户型图 → Room JSON 的七步管线

1. **预处理** —— 透视矫正（单应变换，因为多半是拍照不是扫描）、去噪、二值化
2. **墙线检测** —— 语义分割（CubiCasa5k 系模型）为主，传统霍夫线检测兜底。
   ⚠️ HK 图常见**黑色实心填充 = 承重墙**，细双线 = 间隔墙。**必须区分**——它直接决定吊柜能不能挂这面墙（见 §14）
3. **矢量化** —— 像素线 → 线段 → 正交对齐 → 闭合多边形（polygonize）
4. **★ 比例尺恢复（最容易翻车的一步）**，四法按优先级：
   - **a. OCR 读标注数字**（首选，最准）
   - b. 标准参照物：门 800–850mm、马桶 700mm、浴缸 1500–1700mm
   - c. 用户输入已知总面积反推（差餉物業估價署有记录）
   - d. **兜底：让用户拉一条线输入真实长度**
5. **语义标注** —— 门窗开口位置与宽度、房间标签、固定物
6. **置信度评估** —— 每个房间给一个 confidence
7. **输出 Room JSON + 原图叠加预览**

### 5.3 ★ 人工校正界面（必须有，不是可选）

**这是整条链路上最重要的一屏。** 识别一定会有错，关键是错在哪必须让用户看得见、改得动。

```
┌──────────────────────────────────────────┐
│  原图（半透明 40%）+ 矢量线（叠加）        │
│  · 拖点改线、拖边改长度                    │
│  · 点击输入数值 / 吸附到网格与已有点        │
│  · 低置信度区域黄框高亮                    │
├──────────────────────────────────────────┤
│  比例尺校正：[拉一条线，输入真实长度 __mm]  │
│  补录（图纸上没有的）：                     │
│    □ 层高   □ 梁位置   □ 窗台深度           │
│    □ 來去水位 □ 晾衫位 □ 冷氣機位           │
├──────────────────────────────────────────┤
│  ⚠️ 图纸尺寸 ≠ 现场尺寸，方案已预留 30mm    │
│     请以实地复核为准                        │
└──────────────────────────────────────────┘
```

**为什么这一屏不能省**：家具买回来放不下是灾难性体验，比「方案不够美」严重一个数量级。

### 5.4 图纸上没有、但必须让用户补的东西

户型图只有墙和门窗。**香港的关键约束全都不在图上**：

| 要补什么 | 为什么关键 |
|---|---|
| 层高 | 唐楼 2.4m vs 私楼 2.6m，直接决定高架床能不能做 |
| 横梁位置与下压量 | 不然到顶柜会怼进梁里 |
| 窗台深度（450–600mm） | 白送的储物位 |
| 來去水位 | 决定洗衣机 / 雪柜能不能放这 |
| 煤氣喉 | 硬障碍，且不能改 |
| 晾衫位 | 香港刚需，不能被柜子挡 |
| 冷氣機 / 熱水爐 | 固定占用 |

### 5.5 需求怎么进系统

- **结构化表单**（几房、几个人、预算、必须项）+ **自由文本** + **参考图上传**
- 自由文本 → LLM 解析成 RequirementSpec（见 §4.2）
- 参考图 → CLIP 风格向量，参与选品排序

### 5.6 降级链

```
户型图上传
  ├─ 识别成功   → 人工校正 → Room JSON         （目标路径）
  ├─ 部分失败   → 低置信度区域手工补 → Room JSON
  └─ 完全失败   → 手工画墙 2D 编辑器 → Room JSON （兜底，必须实现）
```

**手工画墙编辑器在第一版就要做**——它是户型图识别失败时的唯一出路，而且实现成本很低（Konva 画布 + 数值输入，不需要任何模型）。

## 7. 家具库：数据从哪来、怎么维护

> §4.2 定义了 SKU schema，但没说数据从哪来。这一节补上。

### 7.1 为什么它比模型重要

**模型是开源的，家具数据不是。** 带精确尺寸、避让空间、感知属性的本地 SKU 库，是唯一抄不走的东西。

### 7.2 数据来源四条路

| 路线 | 说明 | 合规 | 阶段 |
|---|---|---|---|
| 人工录入 | 2 人 2 周录 300–500 个高频 SKU | 干净 | **M0** |
| 官方 affiliate / 商务合作 | IKEA 无公开 HK API，走联盟网络拿 feed | 干净 | M3+ |
| 爬虫 | IKEA HK 商品页规格完整，技术上极易 | ⚠️ ToS 风险 | **仅内部验证，不用于生产** |
| 淘宝 / 天猫（集運） | 品类最全最便宜，HK 人常买 | ⚠️ | M2+ |

### 7.3 感知属性（visual 字段族）怎么标

§4.2 那六个字段不会从商品页上掉下来。三种获取方式：

1. **人工标注**（最准、最慢）：明度与通透度靠看
2. **自动化**：商品主图提取主色 → 转 Lab 明度；材质文本（「實木」「玻璃」「開放式」）→ opacity / openness 分类器
3. **公式合成**：
   `visual_mass_index = footprint_area × height × opacity × (1 - lightness_L/100)`，再归一化

**先人工标 200 个把公式校准对，再上自动化批量跑。** 公式不对，后面所有视觉优化都是错的。

### 7.4 覆盖范围

优先级：IKEA HK → 實惠 Pricerite → 日本城 → DSC → 淘宝/天猫（集運）

目标量级：**M0 500 个 / M2 5000 个 / M4 20000 个。**
不追求全，追求**「一个 300 尺单位会用到的都覆盖」**。

### 7.5 价格与库存刷新

- **价格**：每周刷新。失效时显示「价格待确认」，**而不是给一个错价**
- **库存**：**每个方案必须给 2–3 个替代 SKU**（同尺寸、同功能、不同价位），否则一个下架整个方案作废
- **下架**：不删 SKU，只标 `discontinued`，历史方案仍能打开

### 7.6 尺寸可靠性

厂商标称尺寸与实测有 5–15mm 误差，而且「宽 800」通常指**外框**，柜门打开时还会多占。所以：

> **所有 clearance 按厂商标称 + 20mm 安全余量计算。**

缺尺寸的 SKU（淘宝常见）→ 不录入，或标 `dims_estimated`，仅在用户明确接受时使用。

### 7.7 品类体系

床 / 高架床 / 收納床 / 櫃 / 桌 / 椅 / 沙發 / 層架 / 掛件 / 電器 / 收納箱。

每个品类要定死三件事：**哪些字段必填、clearance 怎么算、能不能被堆叠。** 这是 `packages/schema` 的一部分。

## 8. 单位与数值精度规范（冻结 · v1）

> **这一节不需要再讨论，直接执行。** 改它的代价远大于收益。

### 8.1 核心规则

**内部唯一单位：整数毫米（int mm）。**

| 项 | 规定 |
|---|---|
| 所有长度字段 | `int`，字段名带 `_mm` 后缀 |
| 禁止 | 核心模块（geometry / solver / verifier）出现 float 米 |
| 禁止 | schema 里用无单位数字表示长度 |
| 禁止 | 跨模块传递未 round 的浮点坐标 |

### 8.2 图纸输入与单位转换

支持 mm / cm / 呎吋，**转换只在输入边界做一次**：

```
1 ft = 304.8 mm
1 in = 25.4 mm
「8 呎 6 吋」 = 8 x 304.8 + 6 x 25.4 = 2590.8  ->  round  ->  2591 mm
```

同时**保留原始值**以便追溯：

```json
{"value_mm": 2591, "original": {"value": 8.5, "unit": "ft"}}
```

### 8.3 角度

- 旋转用**整数度**，限制在 `{0, 90, 180, 270}`
- 转角沙发等非正交家具允许 ±5° 容差，**但存储仍为整数度**

### 8.4 几何运算的 epsilon（★ 最容易出事的地方）

浮点比较必须有明确容差，否则「刚好贴合」会被判成重叠：

| 比较 | epsilon | 规则 |
|---|---|---|
| 面积（重叠） | `1e-6 mm²` | **仅当交面积 > 1e-6 才算真重叠**——避免贴边误判 |
| 距离（clearance） | `0.5 mm` | 差距 < 0.5mm 视为满足 |
| 包含（在房间内） | `0.5 mm` | 用 `room.buffer(-0.5).contains(item)`，不用严格 `contains` |

**这三条能消掉 90% 的假阳性「无解」。**

### 8.5 安全余量

| 加在哪 | 加多少 | 理由 |
|---|---|---|
| clearance 计算 | **+20mm** | 厂商标称与实测差 5–15mm |
| 房间尺寸 | **-30mm** | 现场与图纸的误差 |
| 家具尺寸本身 | **不加** | 加在 clearance 上，避免重复扣除 |

### 8.6 求解器约定

- CP-SAT 变量全部 `int mm`
- 位置网格吸附：**50mm**
- 角度：**90° 一档**
- 候选点集生成步长：**50mm**

### 8.7 一条自检

> **如果任何模块的输入类型是 `float` 且代表长度，就是 bug。**

在 `packages/schema` 里用 Pydantic 的 `conint` 强制，让类型系统直接挡住。

## 9. 提议引擎（3D Transformer）

### 6.1 从 v2 变什么

| | v2（2D 单房间） | v3（3D 整屋） |
|---|---|---|
| 预测 | (x, y, rot) | **(x, y, z, rot) + 支撑父节点** |
| 条件 | 单房间多边形 | 房间 + 所属房间标签 + 清单 |
| 粒度 | 整屋一个模型 | **房间级模型 + Level 1 分配器** |

**好消息**：ATISS 本身**已经支持 3D 位置和 on-surface 关系**，方向是对的，直接照抄它的建模方式即可。

**坏消息**：**「整屋家具布局」的学术工作比单房间少得多。** 单房间布局（ATISS、DiffuScene）和户型生成（House-GAN++、HouseDiffusion）都有一堆，但「给一整套公寓排所有家具并跨房间协调」几乎是空白。

**所以：不要训整屋模型。** 训**房间级 3D 模型**（数据充足、有先例），整屋协调交给 Level 1 分配求解器 + Level 3 校验 + LLM 编排。

### 6.2 训练数据：自蒸馏（不变，但目标函数要改）

```
① 用 CP-SAT（目标含视觉指标）在 HK 户型上生成 10 万套整屋方案
② 拆成「单房间 + 清单」的样本对
③ 训 Transformer 模仿求解器
④ 100ms 复现求解器 10s 的结果
```

**关键改动**：造数据时的目标函数不是「最大化储物」，而是**「在放得下全部清单的前提下最大化可见地板占比 + 最小化体量曝光」**。Transformer 学到的就会是「显大」的先验，而不是「塞得满」的先验。

## 11. 审阅层（现在审「显不显大」）

审阅层的 rubric 换掉了一半：

```
□ 家具清单是否全部放下？（must 项一个不能少）
□ 进门第一眼，能不能看到窗？（这是最关键的单项）
□ 有没有任何高家具挡在主要视线上？
□ 大体量家具是否集中在不显眼的位置？
□ 有没有明显的可用性问题？（背光看书、开门撞柜、动线绕床）
□ 预算是否超标？
□ HK 特有的坑：高架床顶梁、挡晾衫位、贴煤氣喉、挡窗台
□ 从渲染图看，整体是"轻"还是"重"？给一个 1-10 的视觉重量分
□ 与用户上一轮的要求是否冲突？
```

**输入必须是渲染图，不是坐标。** VLM 读图判断「显不显大」的能力远强于读坐标判断几何。

## 12. 编排层（三层路由）

v2 的意图分类现在要多一个维度：**这件事归哪一层管？**

| 用户说 | 层级 | 意图 | 通道 | 延迟 |
|---|---|---|---|---|
| 「床别放厨房」 | **L1** | room_assign | 重解分配 | ~1s |
| 「两间房都改成睡房」 | **L1** | 房间重分配 | 重解 L1+L2 | 3–8s |
| 「衣柜放这边」 | **L2** | 位置约束 | 重解该房间 | 1–3s |
| 「这个柜子太高了，显小」 | **L2+L3** | 视觉约束 | 加 sightline 约束后重解 | 1–3s |
| 「有没有矮一点的柜子」 | **选品** | SWAP_ITEM | 目录检索 + 补丁 | <1s |
| 「沙发往左挪 20cm」 | **L2** | MICRO_EDIT | 补丁 | <200ms |
| 「为什么看起来这么小？」 | **问答** | QUESTION | 视觉诊断 | <500ms |
| 「总共多少钱」 | **问答** | QUESTION | 直答 | <200ms |

**新增强意图：`VISUAL_DIAGNOSIS`** —— 用户问「怎么显得这么小」，系统返回 VisualReport 的 detractors 列表 + 修复建议。这是高频需求，而且是零计算（读缓存）就能回答的。

**双通道铁律不变**：能编码成约束 → 重解；否则 → 补丁。绝不为「我喜欢浅色」重跑求解器。

### 13.1 前端

| 2D 画布（户型编辑 / 2D 平面） | Konva / react-konva |

| 后处理（热力图叠加、描边） | @react-three/postprocessing |
| 样式 | Tailwind CSS |
| 客户端状态 | Zustand |
| 服务端状态 | TanStack Query |
| 对话流式 | SSE |

### 13.2 后端

| 用途 | 选型 |
|---|---|
| API | Python FastAPI |
| 求解 | OR-Tools CP-SAT |
| 几何 | Shapely 2.x / Trimesh + manifold3d / NetworkX |
| 数据库 | PostgreSQL + PostGIS（空间）+ pgvector（风格检索） |
| 队列 | Redis + Celery（求解与渲染都是异步长任务） |
| 推理 | 本地 Qwen2.5-VL-7B + 自训房间级 Transformer（2×5070Ti） |
| 对象存储 | MinIO / S3（mesh、渲染图、原户型图） |

### 13.3 ★ 渲染必须分两轨（对 v3 的技术修正）

§15 的性能预算里写「渲染（娃娃屋）3–8s」，暗示用 Blender。**这在交互上是错的。**

| | Three.js / WebGL | Blender headless |
|---|---|---|
| 跑在哪 | 浏览器客户端 | GPU worker 服务端 |
| 速度 | **即时（60fps）** | 3–15s |
| 用途 | 娃娃屋、第一人称、拖拽实时预览 | 照片级效果图、分享图 |
| 何时触发 | 全程 | 只在「出图」时 |

**用户每拖一次沙发等 3 秒，产品就死了。** 实时视图必须是 WebGL，Blender 只做最终出图。

**顺带的好处**：两轨用的是**同一份 Layout JSON**（位置 + 尺寸 + 材质引用），所以浏览器里看到的和最终出的图天然一致。

### 13.4 部署形态

- **M0–M2：单机** —— 你的 2×5070Ti + 32 核那台就能跑全栈，边际成本≈0
- **M3+：拆分** —— 求解 worker 池（CPU 密集，可水平扩）+ 渲染 worker（GPU）+ API
- 前端静态托管，**不需要 SSR**

## 15. 输出与交付物

> 界面里有「导出施工图」「导出料单」两个按钮，但从没定义它们到底是什么。这一节补上。

### 14.1 因为买成品，交付物和传统装修完全不同

传统装修交付「木工施工图 + 板材开料单」——那是因为柜体要现场做。

**买成品家具时木工活基本没有了。用户和师傅真正需要的是另外四样东西：**

| 交付物 | 内容 | 给谁 |
|---|---|---|
| **① 布置平面图** | 带尺寸标注的俯视图，标出每件家具的位置和间距 | 用户、师傅 |
| **② 采购清单** | 型号 / 尺寸 / 价格 / 链接 / 数量 / 替代款 | 用户 |
| **③ 安装位置图** | 吊柜标高、壁挂件固定点、钻孔位置与**墙体类型** | **师傅（最关键）** |
| **④ 水电点位建议** | 插座、灯位、开关的建议位置 | 电工 / 用户 |

**第 ③ 项被严重低估**：买成品不代表不用安装。吊柜、壁挂书桌、电视架都要在墙上打孔——**打在承重墙还是间隔墙、标高多少，师傅需要一张图**。

而承重墙信息在 §5.2 第 2 步就已经识别出来了。**这条信息从输入层一路流到交付物，是整条链路上价值最高的数据之一。**

### 14.2 导出格式

| 格式 | 用途 |
|---|---|
| PDF（A3 平面图 + 清单） | 打印给师傅，最通用 |
| PNG（3D 效果图 + 显大分） | 分享到群组 / 社交媒体 |
| 分享链接 | 只读网页，可旋转查看 3D |
| DXF | 少数需要进 CAD 的场景 |
| CSV 采购清单 | 复制去下单 |

### 14.3 明确不做什么

- **不出木工开料单**（买成品，没有这个需求）—— 这是相对 v1 方案的一个重要减法
- **不给结构改动建议**（见 §19）
- **不代下单**（M5 之后再考虑）

## 19. 评测体系

### 14.1 视觉显大（新增，是核心指标）

| 指标 | 定义 | 目标 |
|---|---|---|
| **可见地板占比** | 关键视点可见地板 / 总面积 | ≥0.65 |
| **进门 isovist 面积** | 入口视点可见面积 | ≥房间面积 ×0.6 |
| **最长视线** | 入口能看到的最远距离 | ≥房间对角线 ×0.8 |
| **遮挡角** | 高家具遮挡的水平角 | ≤0.25 |
| **体量曝光度** | 大体量家具所在格的曝光度加权 | ≤0.3 |
| **显大分（感知）** | VLM / 偏好模型打分 | 相对基线 +15% |

### 14.2 可行性（不变，仍是硬门槛）

硬约束违约数**必须为 0**；储物量不低于清单要求；跨房间动线全通。

### 14.3 人类评测（唯一算数的）

1. 找 10 个真的住小单位的人，用 App 出方案
2. **A/B 盲测**：你的方案 vs 他们现在的实际摆法，问「哪个感觉空间更大？」
3. 拿给装修师傅看：**能不能做？大概多少钱？**
4. 关键问题：**「你觉得 AI 摆的比你自己摆的好吗？」** —— 这是产品成立与否的唯一判据

## 20. 安全、合规与降级

### 19.1 合规

| 项 | 风险 | 做法 |
|---|---|---|
| **PDPO（个人资料）** | 户型图 + 房间照片是个人数据，可能拍到家人 | 默认本地预览；上传需明确同意；可一键删除；**不用于训练除非单独授权** |
| **上传图版权** | 中介图 / 售樓書图有版权 | 仅用于该用户自己的方案；不做公开分享；标注来源 |
| **结构安全** | 用户照方案改墙 | **硬禁止**：永不给出拆墙 / 改间隔 / 改煤氣喉建议，相关提问一律引导到註冊結構工程師 |
| **承重免责** | 用户把重物放吊柜 | 界面明示「承重以产品说明书为准」 |
| **尺寸误差** | 买回来放不下 | 全程 20–30mm 冗余；明示「以实地复核为准」 |

### 19.2 安全约束清单（硬编码，LLM 不可覆盖）

```
· 不可对承重墙提出任何改动建议
· 不可建议改动煤氣喉 / 來去水位主立管
· 高架床顶部必须低于该处梁底
· 只有标注 can_support 的 SKU 才允许被堆叠
· 吊柜必须挂在实心墙（间隔墙须注明需加固）
· 主通道宽度不可低于 600mm
· 涉及儿童安全时提示窗户安全锁
```

### 19.3 降级矩阵（每一环都要想好挂了怎么办）

| 挂了什么 | 表现 | 降级方案 |
|---|---|---|
| 户型图识别失败 | 传了图没结果 | → 手工画墙编辑器 |
| 比例尺读不出 | 尺寸全错 | → 让用户拉线输入真实长度 |
| LLM 不可用 | 意图路由失效 | → 规则路由（覆盖约 70%）+ 按钮式操作 |
| LLM 审阅超时 | 内循环卡住 | → 跳过审阅，出几何最优解并标注「未做偏好审阅」 |
| CP-SAT 超时 | 15s 没出结果 | → 返回 best-so-far + 后台继续算 |
| 完全无解 | 家具放不下 | → 加权最小违约，明确告知「差 X mm」+ 换品建议 |
| 目录缺货 | 指定 SKU 没了 | → 自动给 2–3 个替代 SKU |
| Blender 挂了 | 出不了效果图 | → 降级为 Three.js 截图（质量低但可用） |
| 视觉指标算不出 | 显大分缺失 | → 只出几何可行方案，显大分显示「—」 |

## 21. 风险（v3 更新）

| 风险 | 后果 | 对策 |
|---|---|---|
| **显大与收纳的冲突被优化成"什么都不放"** | 产品无意义 | 家具清单是**硬约束**，清单一律放得下；显大只在可行域内优化 |
| **「显大」是主观的，指标对不上人感** | 优化了但用户不觉得 | 用 VLM 成对比较校准几何指标；找出与人类判断相关性最高的指标组合 |
| 整屋三层分解不收敛 | 反复重解 | 每层设独立收敛判据 + 最多 3 轮 + best-so-far |
| 成品家具库不全，用户买不到 | 方案作废 | 库存/价格定期刷新；每个方案给 2–3 个替代 SKU |
| 承托堆叠导致倾倒 | 安全事故 | 只有标注 `can_support` 的才允许堆叠 |
| 成品尺寸不可调，小空间无解 | 频繁无解 | 软化约束 + 明确告知「差 X mm」+ 建议换品 |
| 高度场处理不当（梁/吊顶） | 柜子怼进梁里 | 高度场进建模，不做事后检查 |
| 渲染慢拖垮交互 | 用户以为卡死 | 2D 秒出、3D 渐进增强（线框→材质→照片级） |
| 视觉指标被"钻空子"（例如全放矮柜） | 违反清单要求 | 清单是硬约束；视觉指标只在可行域内优化 |

| 12 | 撤销 / 版本历史 | **降级保留** | 保留简单的内存撤销栈（便宜，且 UI 已有按钮）；完整版本历史不做 |
| 13 | 冷启动 / Dataset | **做** | 完整方案见 §24 附录 C |
| 14 | 单位与数值精度规范 | **已定，直接执行** | 见 §8，不再讨论 |
| 15 | 多人协作 / 设计师接单 | **不考虑** | — |

### ⚠️ Demo 阶段唯一要盯的指标

> **30 秒内让人说出「哇」。**

对应关键路径只有四条：

1. 传户型图 → 看到它变成 3D
2. 说需求 → 15 秒内出方案
3. 3D 娃娃屋好看
4. 说「为什么显得这么小」→ 诊断 + 一键优化 + **显大分跳动**

**第 4 条是 Demo 的杀手锏。** 前三条别人也能做，第 4 条是只有这套架构才做得出来的东西。

## 24. 附录 C：Demo 阶段的 Dataset 方案

> Demo 的目标是**好看**，不是覆盖全。数据规模比生产方案小一个数量级。

### C.1 Demo 需要四类数据

| # | 数据 | 量级 | 难度 |
|---|---|---|---|
| 1 | 家具 SKU 表（尺寸 / 价格 / 感知属性） | **150 个** | 低（手工） |
| 2 | **家具 3D 模型** | **30 个模板** | **★ 真正的瓶颈** |
| 3 | 户型 | **20 个** | 中 |
| 4 | 自蒸馏训练集 | **~5000 样本** | 低（程序生成） |

### C.2 ★ 3D 模型：Demo 的真正瓶颈，以及它的解法

**问题**：娃娃屋要好看，就需要每件家具的 3D 模型。但——

- IKEA 有官方 3D 模型（Kreativ 用的那套），**拿不到授权**
- 淘宝 / 實惠 没有公开模型
- 3D-FUTURE 有 5000+ 模型，但风格是欧美家具，与 HK 在售 SKU 对不上

**解法：模板 + 尺寸 + 贴图（不要一 SKU 一模型）**

```
30 个品类模板（Blender 脚本程序化生成）
        +
SKU 只存：模板 id + 尺寸 + 颜色 + 贴图
        =
看起来像那件家具 + 尺寸精确 + 渲染快 + 零版权问题
```

**为什么这个方案对 Demo 特别对：**

> **Demo 好看 ≠ 模型精细。好看 = 比例对 + 材质对 + 光照对 + 配色对。**

一个有门缝线、正确倒角、正确材质的立方体柜子，在娃娃屋视角下和精细模型的差别**肉眼几乎看不出**。

**模板清单（30 个）：**

| 品类 | 模板 |
|---|---|
| 櫃 | 兩門 / 三門 / 到頂 / 開放格 / 抽屜櫃 / 電視櫃 / 鞋櫃 |
| 床 | 單人 / 雙人 / 高架床 / 收納床 / 上下舖 |
| 桌 | 書桌 / 書桌+吊櫃 / 餐桌 / 邊桌 |
| 座 | 單椅 / 雙人沙發 / 三人沙發 / 貴妃椅 |
| 收納 | 層架 / 收納箱 / 掛牆架 / 洞洞板 |
| 電器 | 雪櫃 / 洗衣機 / 微波爐 / 冷氣機 |
| 其他 | 茶几 / 屏風 / 鏡 / 晾衫架 |

**贴图来源**：商品主图（正面图）UV 贴到柜门上。**这一步让「看起来像那件家具」成立，是 Demo 里性价比最高的一个技巧。**

**兜底**：某个 SKU 找不到合适模板时，用「带门缝的立方体 + 该 SKU 主色」。**娃娃屋视角下没人看得出。**

### C.3 SKU 表（150 个）

- 全部来自 **IKEA HK**（一家店做深，Demo 不做跨店比价）
- 挑选标准：**高频 + 有价格梯度 + 视觉属性差异大**（这样「显大」的优化才看得出来）
- 每个 SKU 手工标：尺寸 / clearance / mount / can_support / visual 六项
- 工时：**1 人 3 天**

**挑选技巧**：**故意收录同一功能的高低两档**（1.8m 柜 vs 2.4m 到顶柜、深色 vs 浅色同款）。
这样 Demo 时「换个矮柜，显大分从 68 跳到 81」才有得演。

### C.4 户型（20 个）

| 来源 | 数量 | 说明 |
|---|---|---|
| 房委會公开标准户型图 | 8 | 公开免费，且**极有代表性** |
| 自己构造 | 6 | 覆盖极端情况 |
| 网上户型图矢量化 + 人工校正 | 6 | **顺便测试 §5 的识别管线** |

**覆盖类型（缺一不可，Demo 要能演全套）：**

| 类型 | 面积 | 为什么必须有 |
|---|---|---|
| 开放式单位 | ~300 尺 | 最典型、最戏剧性 |
| 一房 | ~400 尺 | 主流 |
| 兩房一廳 | ~500 尺 | 展示跨房间分配 |
| 唐樓 | 高天花 + 怪形状 | 展示高度场 / 横梁 |
| 劏房 | ~100 尺 | **最极端，冲击力最强** |

### C.5 自蒸馏训练集（~5000 样本）

```
20 个户型 × 每个随机 250 组家具清单
= 5000 组 (房间, 清单, 约束) -> CP-SAT 求解 -> 布局
```

- 32 核并行，每组 2–4s → **约 10 分钟跑完**
- 目标函数**必须含视觉指标**（否则学到的先验是「塞得满」，不是「显大」）
- Demo 阶段不需要 10 万，5000 足够把 transformer 训到像样

### C.6 时间不够时砍哪个

| 优先级 | 数据 | 砍掉的后果 |
|---|---|---|
| 🔴 不能砍 | 3D 模板 + 贴图 | 娃娃屋难看，Demo 直接失败 |
| 🔴 不能砍 | 20 个户型 | 没有演示场景 |
| 🟠 尽量保 | 150 个 SKU 的视觉属性 | 显大优化演不出来 |
| 🟡 可以砍 | 自蒸馏训练集 | 退回 CP-SAT 直接求解，慢一点但不影响好看 |
| ⚪ 随时砍 | 跨店比价数据 | Demo 不演示比价 |
