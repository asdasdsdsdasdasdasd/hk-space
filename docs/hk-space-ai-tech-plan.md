# HK 小户型空间优化 App —— 技术方案（多路线对比版）

> 目标读者：项目发起人 / 未来工程负责人
> 一句话定义：用户给出「房间几何 + 想要的家具清单（语义，不是具体 SKU）」，系统输出**在硬约束下可行、且多目标最优的**家具选型 + 摆放方案，并可直接驱动设计软件出图 / 出料单。

---

## 0. 先纠正一个直觉：这不是一个「AI 问题」，是三个

原始想法里「AI 搜索数据库找最佳选项」这句话把三件事混在了一起。它们的技术难度、数据需求、失败模式完全不同，必须拆开做，否则项目一定会卡在中间某个环节上做不出来。

| 子问题 | 本质 | 正确答案用的技术 | LLM 有用吗 |
|---|---|---|---|
| **① 房间 → 结构化几何** | 感知 / 重建 | LiDAR+ARKit、CubiCasa 户型矢量化、VLM 估尺寸 | 辅助（照片估读） |
| **② 家具清单语义 → 具体 SKU + 摆放位姿** | **组合优化 + 装箱** | CP-SAT / 模拟退火 / 学习式场景生成 | 少量（解析需求、审美打分） |
| **③ 出图 / 出料单 / 驱动设计软件** | 几何生成 + 软件自动化 | 脚本化 API >> 像素级点击 | 大量（agent 控制） |

**最关键的一句判断**：②这个环节，用大模型「凭直觉摆家具」是能做 demo 但不能上线的；而用约束求解器（CP-SAT）能保证「不撞墙、柜门能开、人能走过去」。真正该上模型的地方是**审美排序**和**需求理解**，不是可行性。

## 1. 系统总览

```
[输入层] 房间几何输入(4选1)  +  需求文本/清单
   |                              |
   |                    [LLM 解析] → 结构化需求 spec
   v                              v
[Room JSON]  ──────────►  [求解引擎]  ◄──── [家具库 Postgres+pgvector]
 墙/门窗/梁柱/           CP-SAT / SA /        SKU/尺寸/避让空间/
 窗台/固定物             学习式生成           价格/库存/风格向量
   |                          |
   |                     Top-K 方案(带评分与理由)
   v                          v
[3D 预览 Blender/R3F]  [导出 DXF/PDF 施工图]  [AI 驱动设计软件出图/改图]
```

**所有模块间只通过一份 JSON schema 通信。** 这是整个架构里最重要的工程决定：Room JSON 和 Layout JSON 一旦定死，四个输入方案、五种求解方法、三种输出方式就可以任意替换、并行开发、独立评测。

## 2. 输入层：房间几何采集 —— 4 条路线

### A. 纯手工输入（1–2 周可做完，MVP 首选）
- 画布上手绘墙体（Konva / Fabric.js 2D 编辑器）+ 输入长宽；门窗拖拽放置。
- HK 场景必备字段：**层高（唐楼常 2.4–2.6m）**、**窗台深度（常见 450–600mm，是白送的储物位）**、横梁位置、喉管/煤氣喉、露台/工作平台、固定障礙（熱水爐、分體冷氣機）。
- 优点：零硬件依赖、100% 准确、用户可控。**别跳过这一步直接做 AR**，80% 的用户在 MVP 阶段愿意输入尺寸。

### B. iOS RoomPlan（LiDAR 扫描，体验最好）
- Apple 的 `RoomPlan` framework（iOS 16+，需 LiDAR 机型：iPhone Pro / iPad Pro）直接输出参数化房间：墙面多边形、门窗开口、以及可识别的家具类别。
- 代价：**只有 iOS + LiDAR 机型**。Android 没有对等 API（ARCore 只有 Depth / Scene Semantics 原始深度，需要自己重建）。
- 落地：原生 Swift 采集 → 导出 USDZ/JSON → 后端归一化到我们的 Room JSON。
- 注意：RoomPlan 的尺寸误差约 1–3%。**必须留人工校正界面**（拖一条边改长度），否则家具买回来放不下就是灾难。

### C. Android / 无 LiDAR：深度重建
- ARCore Depth API + 自研重建（Open3D / TSDF fusion）→ 平面分割（RANSAC）→ 墙体拟合 → 矢量化。
- 或直接用商用 SDK：Polycam、Occipital Canvas、magicplan SDK、Matterport SDK（贵但省半年）。
- 中等成本，效果不如 B，建议 **P2 阶段**再做。

### D. 照片 / 视频 → 户型（最讨巧，最容易做出差异）
- 户型图照片：用 **CubiCasa5k** 数据集（5000 张标注户型图）训练语义分割 + 矢量化的模型，开源实现可参考。
- 只有现场照片：VLM（本地 Qwen2.5-VL / 云端 Gemini）读图 + 用户提供一个参考尺寸（「这面墙 3.2 米」）→ 反推其余尺寸。精度有限，只适合「先出方案让用户再精修」。
- 混合现实的做法：用户拍 4 张角落照片 + 量一条墙 → VLM 给出初稿 → 手工校正。**这是成本/体验比最高的一条路**。

**推荐**：MVP 用 A，P1 加 B，P2 加 D，C 看用户量再说。

## 3. 家具数据库 —— 这是真正的护城河，不是模型

模型可以开源抄，香港本地 + 淘宝/IKEA 的**带精确尺寸和避让空间的 SKU 库**抄不走。

### Schema（核心）
```json
{
  "id": "ikea-hk-403.006.05",
  "name_zh": "MALM 高架床框",
  "category": "bed",
  "dims": {"w": 1560, "d": 2090, "h": 1000, "unit": "mm"},
  "clearance": {"front": 600, "left": 0, "right": 0, "top": 0},
  "footprint_L": [[0,0],[1560,0],[1560,2090],[0,2090]],
  "storage_volume_L": 420,
  "price_hkd": 2790,
  "url": "https://www.ikea.com.hk/...",
  "stock": "in_stock",
  "style_vec": [0.12, -0.4, ...],
  "assembly": "flat_pack",
  "mount": ["floor", "wall"]
}
```
- `clearance` 是**关键字段**：抽屉拉出、柜门开合、椅子后撤、冰箱散热，全是硬约束。没有它，求解器会摆出一个「不撞墙但打不开门」的方案。
- `footprint_L` 用多边形而非矩形，因为 L 形沙发、角柜很常见。

### 数据获取 4 条路（按合规风险从低到高）
1. **人工录入 + 众包**：先录 300–500 个 IKEA HK / 實惠 / 日本城的高频 SKU。2 人 2 周可完成。**MVP 就靠这个。**
2. **官方 affiliate feed**：IKEA 无公开 HK API，但可通过联盟网络 / 商务合作拿结构化 feed——产品化后走这条路。
3. **爬虫**：IKEA HK 商品页有完整尺寸规格。技术上极易，法律上有 ToS 风险，**只做内部验证，不做持续生产**。
4. **参数化生成（强烈建议叠加）**：用程序生成「任意宽深高 + 柜门/抽屉布局」的虚拟柜体（組合櫃/地台床/高架床）。香港的核心解法往往是**定制傢俬**而非买成品，所以库必须是「可参数化的」，不能只是「离散 SKU 列表」。这一条同时解决「现有成品都放不下」这个香港最真实的痛点。

## 4. 求解引擎 —— 5 种方法（你要的「多种实现方法」核心在这）

### 方法 A：规则引擎 + 贪心放置（1 周，能跑）
- 规则库：床靠实墙、书桌靠窗（自然光）、冰箱靠近厨房入口、衣柜不挡门轴。
- 贪心：按体积/重要性降序，对每个物件在离散候选位姿（贴墙、转角、对齐模数）里选第一个可行解。
- **优点**：可解释（每一步都能说「为什么」）、零训练数据、毫秒级、用户改一个物件能立刻重排。
- **缺点**：容易陷入局部最优；复杂 L 形房间会失败。
- **作用**：这是你的**兜底基线**。后面所有 AI 方法都必须打败它，否则就不值得上。

### 方法 B：CP-SAT 约束求解（2–3 周，生产主力）
用 Google OR-Tools 的 CP-SAT。把房间离散成 50mm 网格或锚点集合：
- 变量：每个物件的 `(x, y, rot∈{0,90,180,270})`
- 硬约束：物件间不重叠（no-overlap / 2D diffn）、在房间多边形内、`clearance` 区域不与任何东西冲突、门口通道可通行。
- 软目标（加权求和）：储物容积最大化、通道宽度最大化、靠墙率、采光面利用、价格。
- 关键技巧：**先用多边形布尔运算（Shapely）算出「可行放置区域」，把连续空间压缩成候选点集**，把 CP-SAT 的搜索空间从无穷降到几千个点。这一步是性能的关键，没做的话求解会超时。

```python
# 伪代码骨架
from ortools.sat.python import cp_model
m = cp_model.CpModel()
for it in items:
    x[it] = m.NewIntVar(0, room_w, f'x{it.id}')
    y[it] = m.NewIntVar(0, room_h, f'y{it.id}')
    r[it] = m.NewIntVar(0, 3, f'r{it.id}')
m.AddNoOverlap2D(...)            # 展开后的矩形/多边形包围盒
m.Maximize(1000*storage_m3 - 3*price_hkd + 200*wall_contact)
```

### 方法 C：随机搜索 / 模拟退火 / MCTS（1 周，做精修）
- 状态 = 一整套摆放；动作 = 移动/旋转某个物件到某候选位姿。
- 打分函数同上；用模拟退火或 beam search 在 CP-SAT 解附近做局部精修。
- 适合：约束太多导致 CP-SAT 无解时「放松-降级」找近似解；以及生成**风格多样的 Top-K**（给用户 5 个不一样的选择，而不是 5 个微调版）。

### 方法 D：学习式场景生成（学术界已成熟的现成路线）
直接复用别人的成果，不要从零发明：
- **ATISS**（NeurIPS 2021，自回归 Transformer 做室内场景合成）——输入房间 + 物件集合，输出位姿序列。
- **DiffuScene**（2024，扩散模型做场景合成）/ **SceneDiffuser**——更现代，生成多样性更好。
- **House-GAN++ / Graph2Plan**——户型/建筑层面的生成，可参考其对「房间连通性」的建模方式。
- **数据**：**3D-FRONT / 3D-FUTURE**（免费、规模大、家具模型接近真实产品风格）、Structured3D、ScanNet、Matterport3D。
- **作用**：不是替代求解器，而是**当"方案提议器"**——快速给出一个大致合理的摆放骨架 + 审美合理性，再由 B 做硬约束校验和微调。这就是学术界常见的「learning proposes, solver disposes」范式。
- 成本：需要一张 GPU 训练，你有 2×5070Ti 可以本地跑微调。

### 方法 E：VLM/LLM Agent 提议 + 几何校验闭环（2 周，性价比很高）
- 把房间画成**带坐标网格的俯视图**（渲染成 PNG，每格 100mm 并标注坐标），连同需求清单一起喂给多模态模型，让它输出 JSON 位姿。
- **然后必须用几何引擎验证**：碰撞？越界？柜门打不开？把违规项以文字反馈回去，让模型自我修正，循环 3–5 轮。
- 这就是 **"generate → verify → repair"** 循环。VLM 对「冰箱别堵门口」这类常识判断比求解器更懂，但对精确尺寸很弱——所以**必须**有校验器兜底。没有校验器的纯 VLM 方案不能上线。
- 优点：不需要训练、几天就能接上、天然支持自然语言微调（「我想要个能看书的角落」）。

### ✅ 推荐组合（P0 → P3 的演进）
```
P0:  A（贪心，跑通闭环）
P1:  A + B（CP-SAT 做主求解，贪心做兜底）  ← 上线版本
P2:  + C（退火做 Top-K 多样性与精修）
P3:  + D/E（学习/Agent 提方案，B 校验）    ← 差异化版本
```

### 多目标必须返回 **Pareto 前沿**，不是单一答案
香港用户不在乎「数学最优」，在乎权衡：「省 3000 块 vs 多 0.8m³ 储物」。
评分维度建议：`fit(硬约束, 0/1)` + `storage_m3` + `circulation(通道最窄处≥600mm, 连通性)` + `daylight(靠窗物件遮挡)` + `cost_hkd` + `aesthetic(VLM 或 CLIP 打分)`。UI 上给 3–5 张卡片，而不是一个分数。

## 5. ⭐ AI 直接控制设计软件 —— 四个层级（你特别问的部分）

先说一条最容易被忽略、但决定成败的判断：
> **对 CAD / 设计软件，"写脚本/写文件" 的可靠性和效率，比 "用 AI 点鼠标" 高 1–2 个数量级。**
> 正确的架构是：**脚本/API 通道做主干，GUI 控制做补充和验收**。全押像素点击的方案一定会因为一个弹窗、一次 DPI 缩放、一次软件更新而全线崩溃。

按可靠性从高到低四级：

### Level 0 —— 程序化生成（不是"控制"，是"直连"，但应该是主干）
| 软件 | 接口 | 能做什么 |
|---|---|---|
| Blender | `bpy` + `--background` 无头模式 | 建房间、摆模型、渲染照片级预览图 / 全景图。**主力渲染器** |
| FreeCAD / OpenCascade | Python API | 精确 CAD、布尔运算、出 DXF |
| SketchUp | Ruby API | 生成 `.skp`（港装修师傅常用） |
| AutoCAD | AutoLISP / .NET / `ezdxf` 直接写 DXF | 出**施工图 / 定制傢俬料单** |
| Rhino | `rhinoscriptsyntax` / Grasshopper | 参数化柜体设计 |
| IFC 生态 | `IfcOpenShell` | 输出标准建筑模型，给设计师/承建商 |

**为什么这条最有价值**：香港装修的终点是「师傅拿图纸开料」。你能直接输出一张 **DXF 施工图 + 板材开料单（cut list）**，这比任何 3D 效果图都值钱——它把 App 从"玩具"变成"能省钱的生产工具"。这是最容易被忽视的杀手锏。

### Level 1 —— 浏览器 DOM/CDP 控制（对 Web 版设计软件最优）
- 目标：**酷家乐 / Coohom**、Planner 5D、HomeStyler、Roomstyler 等 Web 应用。
- 手段：Playwright / CDP 直接操作 DOM 和 JS 状态，**而不是截图像素坐标**。
- 优点：稳定性极高（选择器不随渲染变化），可读取应用内部状态做断言，可注入 JS 批量操作。
- 这就是「AI 控制设计软件」在 Web 场景下的正解：**agent 决定"做什么"，Playwright 决定"怎么点"**。

### Level 2 —— 桌面 GUI 视觉 agent 闭环（通用兜底，也最有"演示效果"）
适用于**没有 API、没有 DOM** 的桌面软件（SketchUp、AutoCAD、酷家乐客户端、Sweet Home 3D）。

标准循环：
```
loop until goal_state_verified or step > MAX:
    1. observe  : screenshot + accessibility tree(UI Automation / AXUIElement / AT-SPI)
    2. ground   : VLM 定位目标控件（推荐用 Set-of-Marks：先在图上画编号框再让模型选编号，
                  比让它直接输出坐标准确得多）
    3. decide   : 输出结构化动作 JSON {tool:"click", ref:"e17"} 或
                  {tool:"type", ref:"e4", text:"3200"}
    4. act      : 执行（优先 a11y 接口，其次坐标点击）
    5. verify   : 重新截图 + 状态 diff，判断子目标是否达成
                 未达成 → 把「期望 vs 实际」写回上下文，重试（最多 3 次）
```
- **已成熟的参照系**：SeeAct、OSWorld、WebArena（学术界 benchmark）、Anthropic Computer Use、OpenAI Operator/CUA、UiPath 的 agent。
- **工程要点（缺一不可）**：
  - **可靠的动作原语层**：把「点击/输入/拖拽/滚轮」封装成带重试和超时检测的函数，不要裸调坐标。
  - **可验证的子目标**：每一步必须有"怎么判断成功"的判据（截图 diff / a11y 属性 / 读取文档状态）。做不到验证的步骤不要交给 agent。
  - **护栏**：动作白名单、最多 N 步、**每步前先 Ctrl+Z 可回退**、破坏性操作（删除/覆盖文件）必须人工确认、跑在沙箱 VM 里。
  - **模态弹窗处理**：专门的"弹窗检测 + 关闭"前置步骤，这是 GUI agent 最大的失败源。
- **成本**：每步一次 VLM 调用。一条 30 步的流程 ≈ 30 次调用。用本地 Qwen2.5-VL 部署在你的 5070Ti 上可以做到几乎零边际成本。

### Level 3 —— MCP 工具层 + agent 编排（推荐的最终形态）
把领域能力封装成 MCP server，让模型调用**语义化工具**，而不是操作像素：

```
scan_room(source)                → Room JSON
parse_requirements(text)         → Requirement spec
query_catalog(spec, room)        → 候选 SKU 列表（含向量检索）
solve_layout(room, items, opts)  → Top-K Layout JSON + 评分
edit_layout(layout, instruction) → 局部修改（"把床换成高架床"）
render_preview(layout, view)     → 图片 / 全景
export_dxf(layout)               → 施工图 + 开料单
drive_design_app(app, task)      → 调用 Level 1/2 驱动酷家乐/SketchUp
verify_against_room(layout)      → 硬约束校验报告
```
GUI 控制（Level 2）在这个架构里退居为 **`drive_design_app` 这一个工具的实现细节**，而不是整个系统的核心。这是最重要的架构决策。

**评测 harness**：准备 30–50 条回归任务（"在酷家乐里新建 3.5×2.8 的房间并放入一张 1.5m 床"），每次改动跑一遍，记录**成功率 / 平均步数 / 平均恢复次数**。没有这个，GUI agent 的迭代就是盲改。

## 6. 技术栈选型（具体到能开工）

| 层 | 选型 | 理由 |
|---|---|---|
| 移动端 | React Native + 原生 ARKit(RoomPlan) 桥接；或 SwiftUI 原生 | RoomPlan 必须原生 |
| Web | React + Three.js / React Three Fiber（3D 预览）+ Konva（2D 户型编辑） | 2D/3D 双视图是刚需 |
| 后端 | Python FastAPI | 几何/优化生态全在 Python |
| 求解 | OR-Tools CP-SAT + Shapely + NumPy | 免费、成熟 |
| 几何 | Trimesh / Open3D / IfcOpenShell / ezdxf | 读写 3D 与 DXF |
| 数据库 | PostgreSQL + PostGIS（空间查询）+ pgvector（风格/语义检索） | 一个库解决空间+向量 |
| 渲染 | Blender headless（bpy）跑在 GPU worker 上 | 照片级效果 + 批量 |
| 模型 | Qwen2.5-VL-7B（本地，需求解析 + GUI agent）；ATISS/DiffuScene 微调（布局提议） | 你有 2×5070Ti 32 核，本地推理可行 |
| 队列 | Redis + Celery / RQ | 求解与渲染是异步长任务 |
| 存储 | S3/MinIO 存 mesh 与渲染图 | |

## 8. 路线图与验收标准

| 阶段 | 周期 | 交付 | 验收标准（硬指标） |
|---|---|---|---|
| **P0** | 2 周 | 手工输尺寸 + 500 SKU + 方法A/B 求解 + 2D 俯视图 | 20 个真实 HK 户型，≥18 个能在 3 秒内出可行解 |
| **P1** | 4–6 周 | 3D 预览 + 避让规则 + Top-5 Pareto + 手工校正 + 分享 | 用户盲测中 ≥60% 认为"比我原来的摆法好" |
| **P2** | 4 周 | RoomPlan 扫描 + 照片估读 + 定制柜参数化生成 + 渲染 | 扫描→方案全流程 ≤5 分钟 |
| **P3** | 6 周 | DXF 施工图 + 开料单 + 酷家乐驱动 + MCP 工具层 | 出图被装修师傅认可可直接施工（找 2 位师傅盲评） |
| **P4** | 6 周 | 学习式布局模型 / VLM agent 提议 | 布局审美人类偏好胜率 > 规则法 60% |

**P0 的 2 周是关键**：如果 P0 做出来用户不觉得有用，后面全是白做。**先证明"优化器比人摆得好"，再谈 AI 和 AR。**

## 9. 评测体系（自己建 benchmark）

- **可行性指标**：违反硬约束数（必须为 0）、求解成功率、平均求解时间。
- **空间指标**：储物容积 m³、最窄通道宽度、地板占用率、窗台/死角利用率。
- **经济指标**：方案总价、每 m³ 储物成本 —— **这是香港用户真正会看的数字**。
- **主观指标**：成对比较（A/B 盲测），用户选择率。
- **回归集**：200 个真实 HK 户型（唐楼、居屋、私楼、劏房各占一部分）+ 30 条 GUI agent 任务。

## 10. 风险与合规（HK 特有，别踩）

- **结构墙不能拆**：AI 绝不能给出"打掉这面墙"的建议。所有承重/改动建议必须免责声明 + 引导找註冊結構工程師。
- **PDPO**：房间扫描数据（含家中影像）是个人数据。默认本地处理、上传需明确同意、可一键删除。
- **尺寸误差**：LiDAR ±1–3%、手工输入误差更大。**所有方案必须留 20–30mm 冗余**，并在 UI 明示"以实地复核为准"。
- **爬虫合规**：见表 3.3，生产环境走官方合作。
- **数据现实**：香港大量户型的真实约束不是"放不下"，而是——層高只有 2.4m（高架床顶到梁）、窗台 500mm（白送储物但要定制）、主力墙位置诡异、必须留出晾衫位。**这些 HK-specific 规则才是产品壁垒，通用 AI 想不到。**

## 11. 竞品与差异化

| 竞品 | 强项 | 缺口（= 我们的机会） |
|---|---|---|
| IKEA Kreativ | 扫描 + AR 摆放，体验好 | **只卖 IKEA**，不是优化，是"摆着看" |
| 酷家乐 / Coohom | 专业级，设计师用 | 面向设计师，非消费者；不解决"买什么" |
| Planner 5D / HomeByMe | 免费易用 | 手工拖拽，无优化引擎 |
| Spacely AI | AI 出效果图 | 出图，不出可行的落地方案 |

**我们的楔子（一句话）**：
> 「不管多小的香港单位，AI 帮你算出**储物最多、走动最顺、最便宜**的那套家具组合——跨店比价，直接出师傅能施工的图。」

即：**跨零售商 + HK 小户型专项优化 + 硬约束保证可落地 + 出施工料单**。前三家各占一角，没人同时做到。
